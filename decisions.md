# Проектные решения

Дата: 18 октября 2026 года. Этап 1 завершён документированием. Требования: [requirements.md](requirements.md).

## 1. Как читать решения

«Из материалов» — прямое требование документов. «Подтверждено пользователем» — ответ в этой переписке. «Решение этапа 1» — выбранное здесь уточнение неоднозначного поведения, открытое для последующей правки, но однозначное для реализации. «Проверить на этапе 3» — техническая гипотеза, не доказанная чтением XML.

Приоритет имеют актуальные явные инструкции пользователя. Затем сохраняются обязательства исходного PDF; продуктовая спецификация их уточняет, а документы этапов определяют порядок выполнения. При расхождении нельзя молча исключить требование PDF или объявить непроверенную SVG-возможность работающей. Принятые здесь разрешения перечислены ниже.

В дальнейшем изменения требований вносятся в оба документа согласованно. Техническую архитектуру, типы и JSON Schema разрабатываем на этапе 4, не выдаём этот этап за выполненный сейчас.

## 2. Принятые решения

### D-01. Границы этапа и репозитория

Из материалов: сейчас выполняется только фиксация требований и решений; программный код запрещён. Git-корень проекта — `peeps-svg-constructor/`, а не родительская папка с материалами. До начала работы в нём находились пустой `README.md` и Git-история. В рамках этапа создаются только `requirements.md` и `decisions.md`; исходные DOCX/PDF/SVG остаются без изменений. Установка пакетов, сборка, прототип и эксперимент SVG не выполняются.

### D-02. Стек

Из материалов: React + TypeScript + Vite, Zustand, IndexedDB, нативный SVG DOM, DOMParser и XMLSerializer; Vitest и Playwright. Решение этапа 1: для интерфейса выбрать CSS Modules, что разрешено подробным заданием этапа 2 и не требует Tailwind. Для IndexedDB допустима Dexie, прямо разрешённая ТЗ; необходимость и окончательное подключение обёртки — на этапах 4–5. SVG.js и тяжёлые библиотеки заранее не добавлять. Версии зависимостей будут закреплены при создании каркаса, совместимость ещё не проверена.

### D-03. Локальное хранение и независимость

Из материалов: три библиотеки в IndexedDB; сохранённая композиция — JSON. Решение этапа 1: экземпляр содержит полный самостоятельный SVG-снимок уже при добавлении. Не использовать отложенное копирование только в момент удаления компонента. Причина: открытый и сохранённый проект должны переживать удаление без каскадных изменений и обязательного поиска всех ссылок.

Связи происхождения исходник → компонент → экземпляр служат метаданными. Удаление не каскадное. Сохранённые данные отделены от UI: режим, zoom, hover, открытые папки и выделение экземпляров не являются содержимым композиции. Точная модель — этап 4.

### D-04. Набор исходников

Подтверждено пользователем: оставшиеся 17 SVG предоставит пользователь, пока работаем с тремя. Не искать и не генерировать им замену в рамках текущего этапа. Требование итоговых 20 SVG сохраняется; до финальной сдачи проверяется наличие 20 иллюстраций в едином стиле. Поставка остальных файлов — внешняя зависимость финальной приёмки, не открытый вопрос о поведении сервиса.

Подтверждено пользователем: разрешено подготовить копии SVG с явными метками логических групп, оригиналы сохраняются. Фактическая подготовка относится к последующим этапам работы с SVG. Решение этапа 1: соглашение о метках — `data-component="true"` на выбираемом `g` либо самостоятельном поддерживаемом графическом элементе. Наличие `id` само по себе не означает выбираемый объект.

Клик поднимается к ближайшему помеченному узлу. Вложенные помеченные объекты могут выбираться отдельно; произвольный выбор произвольного родителя не добавляется. Если выбран и предок, и потомок, итоговое извлечение включает предка один раз. Исходный порядок рисования сохраняется независимо от порядка кликов. Объекты, слитые внутри одного `path`, автоматически не разделяются; предварительная подготовка не должна дорисовывать новую графику.

### D-05. Холст и отображение

Подтверждено пользователем: холст композиции 1200 × 800 SVG-единиц, прозрачный экспорт. Это фиксированный размер для MVP; выбор формата/размера пользователем не добавляется. Исходник показывается с его собственным viewBox, извлечённый компонент — по своим границам. Светлая подложка, сетка и выделение редактора не экспортируются.

Актуальное поведение после D-19/D-21: элементы могут выходить за рабочую область; экспорт остаётся ограниченным 1200 × 800, не подгоняется под содержимое. Новые экземпляры размещаются рядами без изменения собственного масштаба; ряды повторяются в пределах холста. Порядок мультидобавления — порядок отметки компонентов. Дубликат получает смещение +20 по X и Y в координатах композиции, сохраняет прочие параметры; копии помещаются поверх текущей сцены с сохранением их взаимного порядка. Полностью ушедшие за холст экземпляры можно вернуть в центр отдельной кнопкой. Первоначальные решения о размещении всех экземпляров по центру и порядке записей попапа заменены реализацией этапов 8–9.

Масштаб просмотра не сохраняется в JSON композиции и не влияет на операции в её координатах. Численные пределы zoom относятся к деталям интерфейса; никаких обязательств по бесконечному zoom нет. После открытия документа его изображение вписывается в доступную область просмотра без изменения содержимого.

### D-06. Переключение рабочего процесса и отмены

Из материалов: три состояния — пусто, ХИ, ХК; защитный диалог только при несохранённой работе. Решение этапа 1: переход выполняется как незавершённое намерение до выбора следующего документа и успешного прохождения защиты. Пока пользователь отменяет попапы, текущая работа не уничтожается.

Для кнопок создания сначала выбирается следующий исходник/набор компонентов; затем, если нужно, сохраняется/отбрасывается старый черновик; только после этого заменяется активный документ. Двойной клик по известному исходнику/композиции сразу задаёт цель перехода. Подтверждение создания из компонента предшествует защите. Одновременно показывается только один диалог.

«Сохранить» в защитном диалоге — явное согласие сохранить текущую работу; для существующей композиции дополнительное такое же подтверждение не нужно. Для нового компонента/композиции всё равно нужен ввод имени. Любая отмена или ошибка на пути сохранения оставляет исходный документ. «Не сохранять» не удаляет библиотечные записи. «Отмена» прекращает намерение перехода.

Загрузка и экспорт происходят поверх текущей работы без её закрытия. Сворачивание библиотек не вызывает защиту. Повторное открытие того же активного документа не сбрасывает черновик. Перезагрузка/закрытие вкладки при несохранённой работе по возможности использует нативное браузерное предупреждение; собственные три кнопки для закрытия вкладки гарантировать нельзя. Автосохранение черновиков не входит в MVP.

### D-07. Признак несохранённой работы

ХИ: есть непустое выделение для компонента. После успешного сохранения выделение очищается, исходник остаётся открытым. Отмена имени сохраняет выделение. Если выделение пусто, сохранять нечего и при переходе нет защитного диалога.

ХК: сравнивается сохраняемое содержимое с последним успешным сохранением. Добавление, перемещение, поворот, изменение масштаба, дублирование, удаление, смена слоёв делают композицию изменённой. Выделение экземпляров и zoom этого не делают. Возврат к прежнему содержимому означает отсутствие изменений независимо от числа действий.

Новый пустой черновик можно закрыть без защиты. Если из сохранённой композиции удалили все экземпляры, изменения остаются несохранёнными, но пустая композиция не сохраняется. При попытке сохранить пользователь получает объяснение и остаётся в ХК; при «Не сохранять» уходит, оставляя библиотечную версию целой. Экспорт никак не меняет признак сохранённости.

### D-08. Имена, сохранение и перезапись

Из материалов: имена уникальны, до сохранения есть редактируемое значение по умолчанию. Решение этапа 1: уникальность только внутри соответствующей библиотеки; разные библиотеки могут иметь одинаковое базовое имя. Сравнение — trim + Unicode NFC + без учёта регистра, расширение фиксировано и не удваивается. Предлагаемые имена используют тип и ID; при конфликте предлагается новое уникальное значение, пользовательский конфликт не приводит к автоматической перезаписи.

Сохранение компонента всегда создаёт новый библиотечный компонент. Сохранение новой композиции создаёт запись, существующей — заменяет её по ID после подтверждения. Это единственный обязательный сценарий перезаписи; совпадение имени нового объекта не разрешает затереть другую запись. Отрицательный ответ подтверждения перезаписи оставляет изменения на холсте.

Загрузка нескольких файлов: общая очередь, пофайловые ошибки и подтверждения имени; сохранённые позиции не откатываются при отмене следующей. «Отмена» относится к текущему файлу; закрытие окна завершает очередь без сохранения оставшихся, уже сохранённые остаются. Этот процесс не меняет активный документ.

Запись считается сохранённой только после успеха IndexedDB. При ошибке остаются черновик и диалог с причиной/возможностью повторить или отменить. Библиотека не должна показывать фиктивно сохранённую запись.

### D-09. Удаление

Удаление из библиотеки безвозвратно только после отдельного подтверждения. Удаление экземпляра на холсте — редактирование композиции и не удаляет компонент из БЭ; отдельное подтверждение на каждый экземпляр не требуется.

Если удаляемая запись является открытым исходником или композицией, сначала пользователь подтверждает удаление, затем при необходимости проходит защиту несохранённой работы. До успешного завершения всей последовательности ничего не удаляется. Отмена любого шага сохраняет запись и текущий документ. Успех закрывает удалённый документ и возвращает пустой холст.

Для открытой композиции «Сохранить» перед её удалением противоречило бы намерению пользователя: в этом частном случае диалог удаления прямо объясняет удаление также текущих несохранённых изменений и предлагает «Удалить»/«Отмена»; сохранение удаляемой композиции не предлагается. Для исходника выделенный компонент можно сохранить в БЭ через обычную защиту, затем удалить исходник. Отмена сохранения отменяет и удаление. Удаление другого библиотечного элемента не закрывает текущий документ.

Исходник удаляется независимо от извлечённых компонентов; компонент удаляется независимо от экземпляров; композиция удаляется независимо от источников/компонентов. Ссылки происхождения могут стать недоступными, изображения остаются автономными.

### D-10. Выбор и трансформации экземпляров

Решение этапа 1: в ХК обычный клик заменяет выделение, Shift-клик добавляет/исключает экземпляр, фон снимает выделение. Перетаскивание выбранного набора перемещает его целиком с сохранением взаимного расположения. Дублирование и удаление работают для одного или нескольких экземпляров.

Масштаб/поворот через рамку доступны только одному экземпляру; угловой маркер сохраняет пропорции, боковой меняет одну ось. Центр вращения — центр экземпляра. Отражения и изменение точки вращения не входят в обязательный MVP; переход через нулевой размер не должен порождать вырожденную геометрию. Сдвиг слоя — только один экземпляр на один соседний слой, без зацикливания.

Изначальные пропорции при извлечении строго сохраняются. Непропорциональное масштабирование на холсте — разрешённое явное изменение пользователя, а не ошибка сохранения исходника.

### D-11. Перенос SVG и изоляция ID

Из материалов: DOMParser/XMLSerializer и сохранение зависимостей. Решение этапа 1: использовать UUID как префикс пространства ID, согласуя варианты «суффикс»/«префикс» в документах. Существенна уникальность и переписывание ссылок, а не сторона добавления UUID.

Перенос охватывает транзитивное замыкание локальных зависимостей, включая определения, ссылающиеся на другие определения. Если локальная зависимость лежит вне `defs`, её также нужно корректно перенести/нормализовать либо отказать с причиной; нельзя считать наличие ссылки гарантией её расположения в `defs`. Неразрешённые ссылки, неоднозначные дублирующиеся ID и непереносимые циклы не должны молча давать повреждённый результат.

Нужно сохранить эффективное оформление из контекста предков: наследуемые свойства, локальные CSS-правила и преобразования. Копирование всех исходных стилей без изоляции недопустимо: они могут перекрасить соседние экземпляры. Способ фиксации оформления (вычисленные свойства или перенос ограниченных правил с переписыванием селекторов) проверяется на этапе 3. Удаление родительских transform без компенсации запрещено.

Каждое новое размещение и дубликат получают независимую область ID; при экспорте итог дополнительно проверяется на коллизии и целостность ссылок. Извлечение одного объекта несколько раз может давать разные UUID, но одинаковую графику. Исходник не модифицируется даже при ошибке.

### D-12. Границы SVG и техническая проверка

Различаем целевой контракт поддержки и реально подтверждённую поддержку. На момент этапа 1 была подтверждена только структура файлов чтением XML. Результаты выполненного этапа 3 зафиксированы в D-14 ниже и [полном отчёте](docs/stage-3.md).

| Конструкция | Цель MVP / решение | Что проверить на этапе 3 |
| --- | --- | --- |
| `svg`, `g`, `path`, основные статические векторные фигуры | Базовая поддержка | Одиночный/множественный выбор, самостоятельный SVG |
| Вложенные transform, наследуемые fill/stroke/fill-rule | Обязательны для имеющихся Peep | Совпадение вида до/после, границы нескольких объектов |
| Локальные атрибуты, inline style, переносимые локальные CSS-правила | Сохранить эффективное оформление | Каскад, наследование, отсутствие влияния на другие экземпляры |
| `linearGradient`, `radialGradient` и их локальные ссылки | Целевая поддержка | Транзитивные ссылки, единицы координат, повторная вставка |
| `clipPath`, векторная `mask` | Целевая поддержка | Локальные зависимости, координаты, отсутствие обрезания видимой графики |
| Локальный `use` | Условная поддержка после эксперимента | `href`/`xlink:href`, контекст преобразований, перенос цели |
| Фильтры | Не обещать полное покрытие | Либо доказанный ограниченный набор с корректными границами, либо понятный отказ |
| Текст и внешние шрифты | Не входят в гарантируемый набор | Отклонение непереносимого текста; подготовленный векторный контур допустим |
| Внешние CSS/изображения/ссылки, растровые `image` | Не входят в MVP | Понятный отказ без загрузки внешних ресурсов и без растеризации |
| Скрипты, обработчики событий, `foreignObject`, SMIL/анимации | Не поддерживаются | Не исполнять; отклонять с причиной |

Если обязательный целевой случай не проходит, этап 3 не принимается автоматически: зафиксировать результат и ограничения, устранить проблему либо явно согласовать изменение требований. Не расширять молча заявленную поддержку до всей спецификации SVG и не уменьшать обязательства без отчёта.

`getBBox()` проверяется в реальном SVG DOM браузера. Он сам по себе не снимает задачу переноса матриц, stroke и визуальных границ эффектов. Итоговый SVG компонента нормализуется к локальному viewBox с переносом начала координат; нельзя «обнулить transform» ценой изменения рисунка. Для недостоверно вычислимых границ — понятный отказ.

Достоверный эксперимент требует дополнительных небольших SVG-файлов со стилями, градиентами, масками и клиппингом: приложенные три файла таких конструкций не содержат. Эти проверочные файлы не подменяют библиотеку из 20 иллюстраций и не используются как сгенерированные объекты пользовательских композиций.

### D-13. Экспорт

Из материалов: отдельное подтверждение экспорта и сохранение векторности. Экспортируется текущее содержимое холста, даже если оно ещё не сохранено в БК; процесс ХК не завершается. Файл SVG автономен, содержит фиксированную область 1200 × 800, прозрачный фон, векторные узлы и локальные зависимости. По умолчанию имя совпадает с именем композиции с расширением `.svg`, для новой предлагается уникальное имя по ID. Пустой черновик не экспортируется. Импорт результата обратно в редактируемый JSON не обещается.

## 3. Разрешённые расхождения исходных материалов

| Расхождение | Принятое поведение и основание |

## 6. D-14. Подтверждённые решения этапа 3

Дата: 18 октября 2026 года. Изолированный модуль: `experiments/svg/extract.ts`. Полная матрица поддержки, доказательства и ограничения: [docs/stage-3.md](docs/stage-3.md).

- SVG измеряется в настоящем DOM Chrome внутри отдельного Shadow DOM. `getBBox()` не подменяется; данные приложения не влияют на CSS исходника.
- Оформление фиксируется вычисленными SVG-свойствами, переносом родительских групп и transform. Исходные CSS-правила в результат не копируются. Сложные CSS-правила отклоняются согласно матрице поддержки.

- В Peep обнаружены повторяющиеся ID внутри одного файла. Каждому перенесённому узлу назначается отдельный UUID-префикс + номер; повторяющиеся ID без ссылок допустимы. Неоднозначная ссылка на повторяющийся ID отклоняется.
- Границы строятся по локальным getBBox графических элементов с пересчётом в координаты исходного SVG; общий сдвиг нормализует viewBox к `0 0 width height`. При повороте и обводке возможны консервативные прозрачные поля; маски/клиппинг не используются для их сжатия.
- Извлечение части родительской группы с bbox-зависимой маской/clipPath отклоняется с предложением выбрать группу целиком. Объекты, требующие сохранения обрезания исходным viewport, также отклоняются. Это явные границы текущего эксперимента, не обещание универсальной поддержки SVG.
- 36 Vitest-проверок и 12 Playwright-проверок эксперимента пройдены. Для 11 визуальных случаев в Chrome 155.0.8059.80 максимальная разница каналов равна нулю. Это доказательство для данного набора и браузера, а не всех SVG/браузеров.
- Оригинальные материалы и копии `public/demo` не изменены. В `public/experiments` сохранены отдельные подготовленные Peep, отличающиеся разметкой `data-component` и XML-сериализацией.

## 9. D-17. Управление деталями без Alt

По обратной связи пользователя после проверки SVG v2 исправлен контракт взаимодействия: один клик — ближайшая группа, двойной клик — самая мелкая доступная деталь, Shift + клик — добавить/исключить такую деталь. Alt и скрытый контекст входа в группу убраны; Esc снимает выбор.

При Shift-выборе детали внутри выбранного родителя он заменяется деталью, независимые выбранные объекты сохраняются. Так нормализация больше не поглощает намеренный глубокий выбор. Контуры отверстий остаются привязаны к своей детали; «мелкий» не означает разрушение составной геометрии.

Причина и исправление описаны в дополнении к [отчёту](docs/stage-3-v2.md). Добавлены реальные мышиные сценарии для всех 18 деталей лица трёх Peep при 50/100/200%, Shift-набора глаз с экспортом, переключения родителя, прозрачного отверстия и фона. Проверки взаимодействия больше не ограничиваются техническими фигурами и программным выбором. Прежние утверждения D-16 о навигации двойным кликом заменены этим решением; интеграция в основной редактор по-прежнему не выполнялась.
